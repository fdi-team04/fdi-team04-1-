4팀 11/11 발표 피드백 정리와 다음 발표 준비

출처: 11/11 수업 녹음 2개(자동 받아쓰기). 받아쓰기가 많이 깨져 있어 문맥으로 복원했고, 확신이 낮은 곳은 (추정)으로 표시했다. 녹취 끝부분의 "사이즈 부호를 반대로 적용…" 대목은 다른 팀 발표로 보여 제외했다.

한 쪽 요약: 다음 발표까지 할 일 7가지
  1. 잘한 점 유지: 모델 전에 데이터를 먼저 찍어 본 것(9개 변수 5분위 그림)을 좋게 보셨다. 이 방식을 기간별로도 해 본다.
  2. 뉴스도 먼저 찍어 보기: 모델에 넣기 전에 "기사 논조가 좋으면 다음 달 수익률이 높은가"를 같은 방식의 그림으로 보여 준다.
  3. 뉴스를 어떤 단위로 쓸지 정하기: 회사(종목)별 신호인지, 시장·업종 전체의 흐름인지.
  4. LLM 사용 계획과 비용: 전부 유료 API로 분류하면 수십만 원이 들 수 있다. 오픈소스 LLM을 GPU 인스턴스에서 돌리는 대안과 정확도를 비교한다.
  5. 계산 자원과 시간 먼저 정하기: 어디서(클라우드 인스턴스/로컬) 돌릴지, 얼마나 걸릴지 정하고 서둘러 시작한다. 자동 수집(크롤링)은 법·차단 문제를 조심한다.
  6. 학습 기간을 줄여 보기: 해마다 쌓는 방식은 괜찮다. 다만 "데이터를 다 쓰는 게 꼭 좋은가"를 보려고 오래된 앞쪽을 잘라내는 방식(롤링)도 함께 돌려 비교한다.
  7. SHAP으로 XGBoost의 방향 보기: 트리 모델은 +/−를 직접 말해 주지 않지만, SHAP 값을 찍으면 대략 볼 수 있다. 써 보라고 하셨다.

1. 피드백 항목별 상세

칭찬F1. 일단 찍어 본 것이 좋았다

"여기는 오히려 좀 낫다 싶은 생각이 드는 게, 일단 하고 보자 해서 쭉 찍어 본 다음에 된 거잖아요. 그 사이가 되게 좋을 것 같아요. 여러분들도 한번 찍어 보라는 게… 아까 그 9개짜리 표 있는 거, 이런 식으로."

뜻: 변수마다 5분위로 나눠 다음 달 수익률을 본 그림(9개 칸짜리 그림 A)처럼, 모델 전에 데이터로 방향을 먼저 확인한 과정을 좋게 평가하셨다.

준비: 이 방식을 기본 절차로 유지하고, 다음 발표에서도 "찍어 본 그림 → 모델 결과" 순서로 보여 준다.

보완F2. 연도별로, 그룹 수를 바꿔서도 달라질 수 있다

"이게 사실 연도별로 나눠서 또 다를 수도 있고, 그다음에 저 그룹은 10개가 조금 다를 수가 있는데(추정: 10분위로 나누면 달라질 수 있는데), 일단은 이 변수를 할까 말까는 대충 저렇게 보여야… 2번 변수(규모)는 내려가면 내려갈수록 높다는 게 보일 것 같으니까."
"물론 저게 무조건인지는 모르죠. 모델에 반영했을 때 안 오를 수도 있고, 우리가 거르지 못한 어떤 필터링이 있어서 안 맞을 수도 있는데, 적어도 확인할 수 있는 근거는 있어야."

뜻: 그림 한 장(11년 평균)만으로는 부족하다. ① 기간을 나눠도 같은 모양인지 ② 5분위 대신 10분위로 나눠도 같은지 확인하라. 또 미리 보기에서 좋아 보여도 모델에서는 효과가 없을 수 있으니, 둘을 같이 보여 주라.

준비: 9개 변수 그림을 (가) 2011–2015 / 2016–2021, (나) 10분위로 다시 그린다. 방향이 바뀌는 변수는 표시한다. "미리 보기 → 모델 판정" 대응표를 만든다(예: 규모는 미리 보기 강함 / XGBoost 단독 추가는 약함 / FM 강함).

보완F3. 뉴스도 먼저 찍어 보라

"마찬가지로 뉴스도 그런 게 있는지 한번 찍어는 봐야 될 것 같고요."

준비: 모델에 넣기 전에 ① 화제형 기사 논조 5분위 → 다음 달 수익률 ② 기사 있음/없음 그룹의 다음 달 수익률 ③ 기사 수 많음/적음 그룹을 그린다. 분석 코드(step9_news_h3h4.py)는 준비돼 있고, 종목×월 집계 파일만 있으면 된다.

보완F4. 뉴스를 어떤 단위로 쓰는가

"여러분들이 뉴스를 어떻게 쓰는지 몰라서… 뉴스라는 게 회사 단위냐, 종목 단위냐, 아니면 전체에 대한 그 계열의 흐름이 있냐, 어떤 걸 활용하시냐에 따라 다를 것 같은데."
(우리 답) "리스트에 이 회사 이름이 있으면 이 회사 관련해서 모은 다음에… 전체를 넣어 놓은 다음에 기사를 분류해서…"

뜻: 뉴스 변수가 ① 개별 회사(종목)의 소식인지 ② 시장·업종 전체의 분위기인지 발표에서 분명하지 않았다.

준비 (우리 답 정리): 우리는 종목 단위다. 제목에 회사 이름이 있는 기사만 그 회사에 붙이고, 회사×월로 화제형 기사 논조를 평균 낸다. 시장 전체 분위기는 매달 모든 종목에 똑같이 들어가 순위(IC)에는 영향을 주지 않으므로 쓰지 않는다. 이걸 흐름도 한 장(기사 → 회사 매칭 → 유형 분류 → 감성 점수 → 회사×월 → H3/H4)으로 보여 준다.

보완F5. 기사 분류와 LLM 비용

"기사 종류 분류, 이 분류라는 건 어떤 거예요?" (우리 답) "공시형, 화제형, 논란형…"
"써도 상관은 없겠는데, API가 만만치 않을 것 같은데… (기사가 수천 개 단위)라고 하면 다 필터링하면, 저 비슷한 돈은 아니더라도 한 몇십만 원 나올 것 같은데 괜찮아요? … LLM 어떻게 쓰려고 했어요?" (우리) "아직 안 써 봤고…" "그거를 정해 놔야 될 것 같은데."

뜻: 분류 자체는 괜찮다. 하지만 모든 기사를 유료 LLM API로 분류하면 비용이 크니, 어떻게 쓸지 정하라.

준비:

할 것내용
분류 대상 기사 수 확정정리 시험에서 2,641건 → 980건(약 37%)이 남았다. 전체 파일에 같은 비율을 적용해 분류할 기사 수를 추정한다.
비용 계산식기사 수 × (제목+본문 200자 ≈ 입력 토큰 + 출력 약 30토큰) × 모델 단가. 단가는 쓸 모델 기준으로 넣는다.
비용 줄이는 순서① 제목 매칭으로 먼저 거른다(무관 기사 약 40% 제거) ② 키워드로 확실한 것(예: "특징주", "압수수색")은 바로 분류 ③ 애매한 것만 LLM에 보낸다.

보완F6. 오픈소스 LLM + GPU 인스턴스 대안

"예를 들면 (오픈소스 LLM) 같은 오픈 소스 해 놓고, GPU 인스턴스 (빌려서) 그냥 계속 돌려 놓고 하면, 인퍼런스 타임 하면 그것보다 좀 싸게 할 수 있을 것 같고요. 얼마나 정확한지 모르겠지만."

뜻: 유료 API 대신 공개된 LLM(예: Llama·Qwen·EXAONE 계열, 녹취에선 "PM"으로 들림)을 GPU 서버에서 직접 돌리면 추론 비용이 더 싸다. 단, 정확도는 확인해야 한다.

준비: 같은 100건(사람 2명이 정답을 단 것)으로 ① 키워드 규칙 ② 유료 LLM ③ 오픈소스 LLM(Colab/GPU 인스턴스)의 일치율과 처리 시간을 비교표로 만든다. 80% 이상이면서 싼 쪽을 고른다.

보완F7. 계산 자원과 시간을 먼저 정하고 서둘러라

"그건 스크립트야 바로 짜면 될 것 같은데… 돌리려면 시간이 꽤 있을 건데 어떻게 할지… 그래서 일단 대충 먼저 정해 놔야 돌리는 거, 시간 꽤 걸릴 것 같거든요." "여기는 인스턴스 같은 걸 쓰고 있어요, 아니면 로컬에서 하고 있어요?" "계속 감시해 놓을 거 아니면… 좀 서둘러야 될 것 같아요." "일단 최대한 빨리 뉴스를 쓸 거면, 받아서… 이거 어떻게 써야 되는지랑 리소스 괜찮은지랑 대충 시간을 봐야."

준비:

결정할 것제안
어디서 돌리나감성 점수(KR-FinBert-SC)는 Colab T4 GPU로 충분하다. 노트북은 만들어 두었고, 끊겨도 이어서 돌아가게 캐시를 둔다. LLM 분류를 오픈소스로 하면 GPU 인스턴스가 필요할 수 있다.
얼마나 걸리나파일 3~5개로 먼저 돌려 "파일 1개당 시간"을 재고, 전체 시간을 추정해 발표에 적는다.
언제 시작하나수집이 끝난 담당 파일부터 바로 돌린다(전체 마감을 기다리지 않음).

주의F8. 자동 수집(크롤링)의 법적 문제와 차단

(발표 중 질의, 추정) "합법과 불법의 경계… 크롤링으로 공유할 수 있는 걸 스케줄 만들어 놓고 (제한을) 뛰어넘게 한다는 거죠?" "차단당할락 말락 하다가 분명히 걸렸습니다." "그 방법 이전에 다른 방식으로 조회하는 걸 시도하다가 통째로 (막혔고)… 집에 가서 다른 와이파이로 해도 막히더라고요." "어쨌든 법은 있다고 하니, 글쎄요."

뜻 (추정): 자동으로 기사를 긁는 방법을 시도했다가 접속이 차단된 사례와, 그런 방식이 법적으로 애매하다는 이야기다. 교수님은 "관련 법은 있다"며 조심하라는 뉘앙스였다.

준비: 우리는 빅카인즈 화면에서 사람이 직접 받는 방식만 쓰고, 자동 크롤링은 하지 않는다고 분명히 적는다. 남은 회사도 같은 방식으로 받는다(질문했던 "API 말고 다른 방법"의 답).

보완F9. 누적 학습은 좋다. 학습 기간을 줄여 보는 것도 돌려 보라

"이게 이제 올랐을 때, 이렇게 누적하는 건 OK인데, 그때 반대쪽에서 이렇게 당길 필요는 없나 싶은 고민이 들었던 것 같아요. 학습을 꼭 다 써야 무조건 좋구나 하는 건 아닐 것 같긴 해서, 그것도 한번 고민해 보면 좋을 것 같네요. … 어딘가 이렇게 줄어드는 거 해 가지고, 조합은 그냥 돌려 놓고 그냥 냅두고 다른 거 하면 되잖아요. 이제 확인만 하면 될 거니까."

뜻: 지금은 2001년부터 계속 쌓는 확장 윈도우다. "반대쪽에서 당긴다" = 학습 시작점도 같이 앞으로 당겨서 오래된 해를 버리는 것(롤링 윈도우). 20년 전 시장은 지금과 다를 수 있으니, 최근 몇 년만 학습하는 쪽이 더 나을 수도 있다. 여러 조합을 자동으로 돌려 두고 결과만 확인하라.

준비: 같은 단계별 IC를 학습 기간 5년·7년·10년 롤링과 확장(지금)으로 돌려 한 표·한 그림으로 비교한다. 규칙(평균 IC↑ & 6/11년)은 그대로 둔다. 결과를 보고 고르는 게 아니라 "확장이 꼭 나은가"를 보이는 용도라고 밝힌다.

보완F10. 종목마다 뉴스 빈도가 다르다. 메이저만 할 건가

(첫 녹음) "뉴스의 공통적인 건데, 이게 종목별로 뉴스 빈도가 다 있지만, 흔히 말하는 작은 주는 뉴스가 진짜 안 나오고 커질 때 나오는 것 같아서… 그런 건 그냥 무시하고 메이저만 할 건가도 정해야 될 것 같아서." (둘째 녹음) "그런 거 그냥 무시하고 메이저만 하는 거 아닐까도 정해야."

뜻: 작은 회사는 평소 기사가 거의 없다가 주가가 크게 오를 때 기사가 쏟아진다. 그러면 "기사가 있다"는 사실 자체가 이미 오른 종목이라는 신호가 되어 결과가 왜곡될 수 있다. 범위를 대형주(메이저)로 한정할지 정하라.

준비: 우리는 이미 매년 직전 연도 말 시총 상위 100만 수집했다(사실상 메이저). 이를 분명히 밝히고, 평가도 그 100개 안에서만 한다. 추가로 기사 수가 직전 달 수익률과 얼마나 같이 움직이는지 그림으로 보여 주고, 기사 수 자체는 변수로 쓰지 않는다.

보완F11. 트리 모델의 방향은 SHAP 값으로 보라

"트리 부스트(트리 기반 부스팅)는 이게 플러스냐 마이너스냐(포지티브/네거티브)를 모른다는 거, SHAP 밸류 같은 거 찍으면 얼추 볼 수 있거든요. (SHAP)이라고 검색하면 나오니까 그거 한번 써 보세요."

뜻: 우리가 "XGBoost는 방향을 알려 주지 않아서 Fama-MacBeth로 따로 본다"고 했는데, SHAP을 쓰면 XGBoost 안에서도 변수가 클 때 예측이 올라가는지 내려가는지 대략 볼 수 있다.

준비: 수급까지 넣은 XGBoost 모델로 SHAP summary plot과, 개인 순매수·규모·단기 반전의 dependence plot을 그린다. Fama-MacBeth 방향과 같은지 대조표를 만든다. 팀 저장소 requirements.txt에 shap이 이미 있고, 06_explain.py에 자리(shap_dependence)도 있다.
